# プロダクト判断

## 1. ゲストモードを先に置き、登録を後に回す

**状況**
習慣化アプリは「使い始めるまでの摩擦」が離脱に直結します。初回起動でアカウント作成を求めると、価値を体験する前に離脱するユーザーが出ます。

**選択肢**

| 案 | 内容 | 懸念 |
|---|---|---|
| A | 起動時にアカウント作成必須 | 実装が単純。離脱率が高い |
| B | 完全ローカル保存、同期なし | 摩擦ゼロ。機種変更でデータ消失、フレンド機能が作れない |
| C | ゲストセッションをサーバー側に作り、後から本アカウントへ昇格 | 摩擦が小さくデータも守れる。**認証経路が 2 本になる** |

**判断**
**C を採用。** 認証を 2 経路持つ複雑さは、離脱率の改善に見合うと判断しました。

実装は認証クラスを分けることで吸収しています。

| 種別 | ヘッダー | 認証クラス |
|---|---|---|
| 通常ユーザー | `Authorization: Token <token>` | `ExpiringTokenAuthentication` |
| ゲスト | `Authorization: GuestToken <token>` | `GuestTokenAuthentication` |

View 側は `get_player_for_request()` で両者を透過的に扱うため、**個別の API は認証経路を意識しません**。

**結果**
狙いどおり摩擦は下がりましたが、**昇格時の衝突処理が想定より複雑**でした。「ゲストで使っていたが、実は過去に同じ Google アカウントで登録済み」というケースで、どちらのデータを残すかをユーザーに選ばせる専用エンドポイント（`/auth/social/promote-confirm/`）が必要になりました。

さらにこの経路は**本番で 500 エラーを踏んだ箇所**でもあります（→ [§8](#8-トランザクション内の例外捕捉に入れ子-savepoint-を必須化した)）。

**学び**: 「認証経路を 2 本持つ」判断のコストは、認証そのものではなく**2 本が合流する地点**に集中して現れました。

## 2. ガチャの天井を廃止し、チケット上限を大幅に緩和した

**状況**
初期実装ではソーシャルゲーム的な定石をそのまま持ち込んでいました。

- ガチャに**天井**（一定回数引けば確定で高レア）
- チケット保有上限を Daily 5 / Weekly 4 / Monthly 3 枚に設定

しかしこれらの数値には**根拠がありませんでした**。実装当時に「それらしい」値を置いただけで、検証していません。

**選択肢**

| 案 | 内容 |
|---|---|
| A | 現状維持。ソシャゲの定石に従う |
| B | 上限だけ緩和する |
| C | **天井を廃止し、上限も大幅に緩和する** |

**判断**
**C を採用。** 判断の根拠は 2 つあります。

1. **チケット上限が「サイレントな損失」を生んでいた** — 習慣を継続してもチケットが上限に達していると、報酬が**何の通知もなく消えていました**。これは「休んでも壊れない」というプロダクトの中核と真正面から矛盾します。上限を Daily 30 / Weekly 10 / Monthly 3 に引き上げ、実質的に損失ゼロにしました。
2. **天井はプロダクトの思想に合わない** — 天井は「回さないと損」という圧力を作る仕組みです。Sabiowl の報酬は課金ではなく**習慣の継続**から来るため、圧力をかける装置は不要でした。

**結果**
ゲームバランス定数は `backend/api/constants.py` に集約し、**変更理由をコメントとして残す**運用にしました。「昔の誰かが置いた根拠不明の値」を作らないためです。

```python
# 旧 5/4/3 は BUG-62 実装時の arbitrary spec。
# 2026-07-29 のユーザーフィードバックを受けて silent loss を実質ゼロ化。
```

**学び**: **「業界の定石」は、自分のプロダクトの目的と照合してから採用する。** 定石をそのまま入れた結果、中核思想と矛盾する挙動が生まれていました。

## 3. 祝祭系モーダルの自動クローズを禁止した

**状況**
レベルアップやガチャ結果などの「祝祭系」ポップアップを、アニメーション完了時に自動で閉じる実装にしていました（`AnimationController.addStatusListener` 経由）。

**問題**
- ユーザーが結果を読み切る前に消える
- アニメーション完了と画面遷移が競合し、**遷移先で黒画面になる**ケースがあった
- 端末性能によってアニメーション時間が変わるため、**再現性の低いバグ**になった

**判断**
**祝祭系ポップアップの自動クローズを全面禁止**し、閉じるのは X ボタン・明示的なボタン・戻るジェスチャの**ユーザー操作のみ**としました。SnackBar / Toast のような ephemeral な要素は例外です。

**結果**
UX とバグの両方が同時に改善しました。「見せたいものを勝手に消さない」という原則が、たまたま並行性のバグも消しました。

**学び**: **タイマーやアニメーションを画面遷移のトリガーにしない。** ユーザー操作を起点にすれば、タイミングが決定的になります。

## 4. 稼働中の本番 DB でモデルを 4 分割した

**状況**
`PlayerProfile` が 30 以上のフィールドを持ち、経済（ダイヤ・コイン）・戦闘（レベル・EXP）・ストリーク・設定が 1 モデルに混在していました。アーキテクチャレビューで「責務混在」として指摘されました。

**すでに本番稼働中**で、実ユーザーのデータが入っている状態です。

**選択肢**

| 案 | 内容 | リスク |
|---|---|---|
| A | 分割しない | 技術的負債が増え続ける |
| B | 一度のマイグレーションで分割 | 単純。**失敗したら本番データを失う** |
| C | **段階的に分割する** | 工数は増えるが各段階で戻せる |

**判断**
**C を採用。** 4 段階に分けました。

```
Phase 2a  4 モデルを CreateModel で追加（既存フィールドはそのまま残す）
Phase 2b  データをバックフィルし、新旧両方に書き込む期間を設ける
Phase 2c  読み取りを新モデルに切り替え、dev 環境で破壊的検証
Phase 2d  PlayerProfile 側の旧フィールドを RemoveField
```

移行期間中は `__getattr__` / `__setattr__` による**後方互換シム**を置き、既存コードが `player.diamonds` のまま読み書きできる状態を維持しました。

**結果**
本番影響ゼロで完了しました。ただし重要なのはシムの扱いです。

**シムは「消し忘れると恒久化する」性質を持ちます。** これを防ぐため、シム導入と同時に

- 削除条件をコード内に明文化する
- **削除作業を別チケットとして起票する**（FEAT-488）

を行いました。「あとで消す」を人間の記憶に委ねない仕組みです。

**学び**: 稼働中システムの構造変更は、**戻せる単位に切る**ことが工数以上に価値があります。そして**暫定対応には必ず出口を設計する**。

## 5. カテゴリ → ステータスを「単一割当」から「比率按分」に作り直した

**状況**
習慣のカテゴリを 4 種類に統一し、それぞれを 6 軸ステータスのどれか 1 つに割り当てる設計でした。

**問題**
「仕事」のような習慣は、学習力にも貢献力にも寄与するはずです。しかし単一割当では片方しか増えません。しかも**ユーザーには何も表示されない**ため、寄与が消えていることに気づけませんでした。

**判断**
カテゴリを 11 種類に増やし、**比率による按分**方式へ全面的に作り直しました。

```python
CATEGORY_STAT_MAP: dict[str, list[tuple[str, float]]] = {
    '仕事': [('学習力', 0.5), ('貢献力', 0.5)],
    '休息': [('健康力', 0.5), ('精神力', 0.5)],
    'その他': [(s, 1/6) for s in ALL_STATS],
    ...
}
```

**結果**
実装上の副作用として、**1 回の習慣完了で複数の `CharacterStat` を更新する**必要が生まれました。ここに並行性の問題が発生します。

複数行を同時にロックするため、取得順序がバラバラだとデッドロックします。そこで**`select_for_update()` は必ず pk 昇順**というルールを設けました。

```python
CharacterStat.objects.select_for_update().filter(...).order_by('pk')
```

**学び**: 仕様の作り直しは「作り直しコスト」だけでは終わらず、**新しい失敗モードを連れてくる**。今回は「単一行更新 → 複数行更新」の変化がデッドロックのリスクを生みました。仕様変更のレビューでは、**データアクセスパターンがどう変わるか**を見る必要があります。

## 6. 既存の手動 Riverpod Provider を移行しないと決めた

**状況**
プロジェクト途中で `@riverpod` アノテーション（コード生成）を導入しました。型安全な `family` や自動 `autoDispose` が得られ、明確に優れています。

一方、既存の 7 feature（`social` / `settings` / `timeline` / `quest` / `sabi` / `achievement` / `rest_day`）は手書きの Provider で実装済みで、**正常に動作しています**。

**選択肢**

| 案 | 内容 |
|---|---|
| A | 全部 `@riverpod` に移行して統一する |
| B | **新規のみ `@riverpod`、既存は移行しない** |
| C | 移行せず、新規も手動で書いて統一する |

**判断**
**B を採用。** そして重要なのは、**この判断を規約として文書化した**ことです。

> 既存の手動プロバイダー feature（`social` / `settings` / ...）は**移行しない**。
> 既存の手動プロバイダーに `family` を追加する場合のみ、その provider のみ `@riverpod` 化を検討する。

**結果**
コードベースに 2 つのスタイルが共存しますが、**それが意図的であることが読めば分かります**。

文書化しなかった場合、後から読む人（あるいは AI）は「移行し忘れ」と解釈して、動いているコードを触るリスクがありました。実際に本プロジェクトでは AI が実装を担う場面が多いため、この明文化は繰り返し効いています。

**学び**: **「やらない」判断こそ記録する価値がある。** 「なぜ古い書き方が残っているのか」に答えられない状態は、いずれ誰かが不要な移行を始めます。

## 7. DB を Render PostgreSQL から Neon へ移行した

**状況**
Backend は Render で稼働しており、DB も Render PostgreSQL を使っていました。テスト期間終了後の従量課金移行を控え、コスト最適化とスケーリングを検討する必要がありました。

**選択肢**
3 サービスを比較しました。

| 観点 | Render | **Neon** | Supabase |
|---|---|---|---|
| コスト（小規模時） | 固定課金 | **従量課金 + 無料枠** | 無料枠あり |
| スケーリング | 手動プラン変更 | **自動スケール** | 自動 |
| **DB ブランチ** | なし | **あり** | なし |
| Backend との併用 | 同一 | 別サービス | 別サービス |

**判断**
**Neon を採用。** 決め手はコストではなく **DB ブランチ機能**でした。

本番のスナップショットから `dev` ブランチを切れるため、**本番と同じデータ形状で破壊的な検証ができます**。マイグレーション 200 本を運用するプロジェクトにおいて、これは安全性への直接的な投資でした。

**実行にあたっての備え**:
- 本番全ユーザーに影響する変更のため、リスク評価を事前に文書化
- **旧 Render DB を 1 週間保持**してロールバック経路を確保
- `pg_dump` / `restore` の失敗に備えた手順を用意

**結果**
移行は成功し、その後 dev 環境の構築（`sabiowl-backend-dev.onrender.com` + Neon `dev` ブランチ + Firebase / PostHog / RevenueCat の別プロジェクト）につながりました。**本番相当の環境で壊せる**ことが、以降の大きな変更（モデル 4 分割など）を可能にしています。

**なお、この移行のタイミングについては v1.0 リリース直前であり、リリース後を推奨する意見もありました**。最終的にリリース前実施を選択し、結果として問題は発生しませんでしたが、**判断が分かれた点として記録しています**。

**学び**: インフラ選定は「今の請求額」ではなく「**どんな作業が安全になるか**」で選ぶ方が効きました。

# 運用・品質判断

## 8. トランザクション内の例外捕捉に入れ子 savepoint を必須化した

**状況**
ゲストから Google アカウントへ昇格する経路で、本番で **500 エラー**が発生しました。特定のユーザーが「何度試してもサインインできない」状態になりました。

**原因**
PostgreSQL 固有の挙動です。

```python
@transaction.atomic
def post(self, request):
    try:
        SocialAccount.objects.create(...)   # ← IntegrityError
    except IntegrityError:
        # ここに来た時点で PostgreSQL の接続は「aborted」状態。
        # 以降のあらゆるクエリが InFailedSqlTransaction で失敗する。
        existing = SocialAccount.objects.get(...)   # ← 500
```

SQLite（ローカル開発環境）では**この問題が再現しません**。そのため開発中は発覚せず、本番でのみ露出しました。

**判断**
`@transaction.atomic` の内側で `IntegrityError` を捕捉する場合は、**入れ子の savepoint を必須**としました。

```python
@transaction.atomic
def post(self, request):
    try:
        with transaction.atomic():      # ← savepoint を作る
            SocialAccount.objects.create(...)
    except IntegrityError:
        # savepoint までロールバックされるので接続は生きている
        existing = SocialAccount.objects.get(...)
```

**結果**
契約テストを追加して縛り、プロジェクト規約に落としました。

さらに構造的な問題として、**ローカル SQLite と本番 PostgreSQL の差異**が浮き彫りになりました。CI は PostgreSQL で実行するようにしており、この種の差異を CI で捕まえられる状態にしています。

**学び**: **「ローカルで再現しないバグ」は環境差そのものを疑う。** そして再発防止は「気をつける」ではなく、**規約 + テスト + CI 環境の一致**で行う。

## 9. 破壊的マイグレーションを禁止し、同時に「例外条項」を定義した

**状況**
マイグレーションの `RunPython` 内でデータを削除・一括更新する実装が入っていました。マイグレーションは本番で自動実行されるため、**誤りがあっても止められません**。

**判断（第 1 段階）**
`RunPython` での `.delete()` / 大量 `update()` を**禁止**し、management command での明示的な手動実行に寄せました。

```
python manage.py cleanup_stale_users --dry-run   # まず確認
python manage.py cleanup_stale_users --confirm   # 明示的に実行
```

**判断（第 2 段階）— 禁止だけでは回らなかった**
運用してみると、**禁止では処理できないケース**が実在しました。

- マスターデータの投入（chicken-and-egg 問題: データがないとアプリが起動しない）
- Shell が使えない環境での 1 回限りの処理

ここで「禁止を貫く」のではなく、**例外の境界を定義する**方向に切り替えました。

| 例外条項 | 条件（すべて満たす場合のみ） |
|---|---|
| **1 回限り例外** | ① chicken-and-egg である ② Shell 実行が不可能 ③ 1 回限りである + management command を並行維持 |
| **master data 例外** | ① 対象が master data のみ ② FK を網羅している ③ 冪等である |

**結果**
ルールが実運用に耐えるようになりました。禁止のままだと**抜け道が非公式に使われる**か、**ルールごと無視される**かのどちらかになっていたはずです。

**学び**: **守れないルールは、ルールの側に欠陥がある。** 例外を認めないより、**例外の条件を明示する**方が結果的に規律が保たれました。

## 10. 「移行完了」と報告した作業が未完だった

> この項目は失敗の記録です。

**状況**
API のエラーレスポンス形式を新形式に統一する作業（FEAT-475）で、**「全 view の移行が完了した」と記録していました**。

根拠は次の検索でした。

```bash
grep "Response({'error'" backend/api/views/   # → 0 件
```

0 件なので完了、と判断していました。

**何が起きていたか**
実際には**旧形式が 78 件残っていました**。検索がヒットしなかったのは、コードが改行を挟んで書かれていたからです。

```python
return Response(              # ← ここで改行するので
    {'error': '...'},         #    "Response({'error'" では 1 件もヒットしない
    status=400,
)
```

正しくは `Response\(\s*\{\s*'error'` で検索する必要がありました。

**影響**
旧形式にはエラー `code` が無いものがあり、**クライアント側で code から文言を解決する経路に乗りません**。この状態で「次フェーズ = 旧 parser の削除」を実行していたら、**78 経路のエラー表示が一斉に壊れていました**。

幸い、次フェーズ着手前の確認で発覚しました。

**判断**
1. 実測値をドキュメントに訂正記載する（新形式 73 件 / **旧形式 78 件**）
2. 「旧 parser 削除を先に実施してはいけない」という警告を、該当箇所に**明示的に書く**
3. 移行と英語化を別チケット（FEAT-515）として再起票する

**結果 / 学び**

- **grep の 0 件は「存在しない」の証明にならない。** パターンが対象を捉えられていない可能性が常にあります。「0 件」を完了根拠にするときは、**わざと 1 件ヒットさせて検索式の妥当性を確認する**べきでした。
- **完了の記録が誤っていると、後続の判断が連鎖的に狂う。** この件では「Phase 3 完了」という誤記録に基づいて「Phase 4 は安全に実施可能」と書かれていました。誤りは 1 箇所でも、影響は下流全体に及びます。
- ドキュメントを訂正する際は、**元の記述を消さずに「なぜ誤ったか」を残しました**。同じ検索の誤りを繰り返さないためです。

## 11. 正規表現による一括書き換えをやめた

> この項目も失敗の記録です。

**状況**
英語化フェーズ（多言語対応・API 形式統一）で、**3 日間に作り込んだ欠陥 7 件のうち 6 件が「スクリプトによる一括書き換え」由来**でした。手で書いたアプリケーションコードでの欠陥はゼロです。

| 内容 | 出どころ | 検出経路 |
|---|---|---|
| `extra` key 欠落 16 箇所 | 一括変換スクリプト | テスト 5 件が KeyError |
| フィールド名の誤生成・誤マッチ | 一括変換スクリプト | `makemigrations` 出力 |
| import 挿入位置ミス ×3 | 一括変換スクリプト | SyntaxError |
| 内側クォートで regex が停止 | 一括変換スクリプト | テスト失敗 |
| 行番号キーのずれ | 一括変換スクリプト | 手動確認 |

**原因分析（3 層）**

1. **正規表現でソースコードを書き換えていた** — 正規表現が扱えるのは正規言語ですが、Python / Dart は文脈自由文法です。**クラススコープ・ネスト・論理行・文字列内のクォートは原理的に regex の表現力の外**にあります。「もう少し賢いパターン」で近似しようとすると、毎回別の場所で破れます。上の 5 件は**同じ 1 つの原因の別の顔**でした。

2. **スクリプト化の判断が早すぎた** — 78 箇所と分かった瞬間に反射的にスクリプトを書きました。手作業なら 1 箇所 30 秒 × 78 = 約 40 分、誤爆は最大 1 箇所です。実際にはスクリプト作成 + 誤爆 + 復元 + **修復用スクリプトの追加作成**で超過し、誤爆は全 78 箇所に波及しました。

3. **作業の性質が変わっていた** — 多言語化や API 形式統一のような横断的作業は「N 箇所を同時に変える」形をしています。「1 機能を新規実装」フェーズではこの失敗モードは発現しません。**腕の問題ではなく、作業形態が変わると別の弱点が露出する**ということでした。

**判断**
対策を「効果 / コスト」で評価し、上位 2 つを無条件実行にしました。

| # | 対策 | 7 件のうち防げた数 | コスト |
|---|---|---:|---|
| 1 | 一括書き換え後に**必ず構文検証**（`python -m compileall -q` / `dart analyze`） | 3 | 1 行 |
| 2 | **1 ファイルで試して `git diff` を目視 → 全件** | 5 | 2 分 |
| 3 | 変換前に**変換元のバリエーションを全列挙** | 1 | 1 コマンド |
| 4 | スクリプト化の閾値を **30 箇所**に引き上げ | 予防的 | ─ |
| 5 | regex ではなく `ast` / 明示的スコープ走査を使う | 5 | 中 |

**#1 と #2 だけで 6 件が防げていました。合計コストは数分です。**

**結果 / 学び**

- **#3 が最も重要でした。** `extra` key の欠落は regex の誤爆ではなく、**変換先の表現力が変換元より狭いことに気づかなかった**という別種のミスです。「変換先が変換元を包含するか」を事前に検算する必要がありました。今回はたまたま既存テストが検出しましたが、**テストでは捕まえにくい類**です。
- **検出と発生を混同しない。** 上記 7 件はすべて同一セッション内で自ら検出・修正しています。「ミスが増えた」ように見えるときは、**発生が増えたのか可視化が進んだのか**を切り分ける必要があります。ただし検出が効いていても、**発生を減らす方が常に安い**。

## 12. CI を段階的に fatal 化した

**状況**
CI を導入した時点で、`flutter analyze` には 13-15 件の指摘（baseline）が存在していました。

**選択肢**

| 案 | 内容 | 問題 |
|---|---|---|
| A | 全部直してから CI を fatal で導入 | 導入が遅れる。その間に新規の指摘が増える |
| B | CI を入れない | 論外 |
| C | **`continue-on-error: true` で先に導入し、後から締める** | 「警告が出ても通る」状態が常態化するリスク |

**判断**
**C を採用。** ただし C の最大のリスクである「常態化」を避けるため、**移行の意図を CI 設定ファイル自体にコメントとして書きました**。

```yaml
# Phase 1 (deprecated): flutter analyze は continue-on-error: true (baseline 13-15 issues)
# Phase 2 (現行、2026-07-25 昇格): 全 job strict、fatal 化。
```

**結果**
2026-07-25 に全 job を fatal 化しました。`flutter analyze` のみ `--no-fatal-infos` で info レベルを許容していますが、これも「将来 info もゼロに到達したら `--fatal-infos` に切替可能」と設定ファイルに明記しています。

加えて、**プロダクト固有の lint を pre-commit で自作**しました。

```yaml
- id: no-raw-exception-in-ui     # UI の Text に生の例外を出さない
- id: no-raw-error-tostring      # e.toString() をユーザーに見せない
```

これは「ユーザーに技術的なエラー文字列を見せない」というプロダクト原則を、**レビューではなく仕組みで守る**ためのものです。

なお、この lint は導入直後に**誤検知で CI を赤くしました**。初版の正規表現 `Text.*\$e` が `$expGain` `$error` `$element` などにもマッチしていたためです。単語境界 `\b` を追加して修正しました。

**学び**: **暫定的な緩和は、緩和の期限と条件を設定ファイル自身に書く。** 「あとで厳しくする」を人の記憶に置くと、まず実行されません。

## 13. 公開用スナップショットを別リポジトリに切り出した

### 課題

このプロジェクトを公開したいが、開発リポジトリをそのまま public にはできない。

理由は 2 つありました。

1. **git 履歴に Firebase のサービスアカウント秘密鍵が残っている。**
   2026-04-24 に誤ってコミットし、2026-05-22 に HEAD から削除しましたが、
   **HEAD から消しても履歴からは消えません**。`git log` で誰でも取り出せます。
2. **運用文書に本番インフラの識別子が含まれる。**
   実測したところ、追跡ファイル 2,130 件のうち Neon の本番 endpoint を含むものが
   10 件、App Store の審査対応記録が 33 件ありました。

### 選択肢

| 案 | 履歴の秘密鍵 | 判断 |
|---|---|---|
| リポジトリを public 化 | 露出する。`git filter-repo` での書き換えが必要 | ❌ 1,732 コミットの書き換えは取り消しが効かず、取りこぼしのリスクが残る |
| ブランチを分けて公開 | — | ❌ **成立しない**。GitHub の公開設定はリポジトリ単位で、ブランチ単位ではない |
| **別リポジトリにスナップショットを切り出す** | 持ち込まれない | ✅ 採用 |

3 つ目を選びました。履歴を切り離すことで、鍵の問題を「回避」ではなく
**構造的に無効化**できます。公開側には private 側の履歴が存在しないためです。

### 判断

同期スクリプト（`scripts/portfolio/`）を作り、3 段構えで守る設計にしました。

| 層 | 仕組み | 守るもの |
|---|---|---|
| 1 | コピー元を `git ls-files` に限定 | `.gitignore` 済みファイル（鍵 / `.env` / venv）の混入を**構造的に不可能**にする |
| 2 | `exclude.txt` | 見せる必要がないもの（運用文書・審査記録）を減らす |
| 3 | `secret_patterns.txt` | 出てはいけないものを止める。1 件でもヒットしたら同期を中断 |

**この 3 層は役割が違います。** 除外リストは「今わかっている機微」しかカバーできず、
半年後に運用文書が増えても自動では追随しません。実際に公開を守っているのは
**層 3 のパターン走査**です。層 2 は公開物を整えるための道具にすぎません。

誤検知には `allowlist.txt` で個別に例外を与えますが、**理由の記載を必須**にし、
**使われなくなった行はエラー**にしました。放置された許可行は
「昔は誤検知、今は本物」を隠すためです。

さらに、この走査を **private 側の CI にも入れました**。同期の直前にしか
気づけないと、混入から発覚まで数週間空き、その間のコミットを全部さかのぼる
ことになります。CI で止めれば当該 PR で済みます。

README は公開版を別ファイルとして持たず、**private 版に置換ルールを適用して生成**
します。333 行の README を 2 本持つと、片方だけ更新されて必ず drift するためです。
置換元の文言が見つからなければ同期を中断し、除外したファイルへのリンクが
残っていればリンク切れとして検出します。

### 結果

追跡 2,130 件 → 公開 1,277 件（853 件を除外）。導入時の走査で 14 件を検出しました。

| 検出内容 | 対処 |
|---|---|
| Firebase の Web API キー 7 件 | ファイルごと除外（自動生成の設定で、読み手にとっての価値がゼロ） |
| CI / `.env.example` のダミー値 5 件 | 理由つきで許可リストへ |
| テストフィクスチャ 2 件 | 同上 |

また、走査とは別に **コードに開発者本人の実メールアドレスが 2 箇所**
（`email_mask.dart` の docstring とそのテスト）残っているのを見つけ、
ダミーアドレスへ置き換えました。

5 通りの壊し方（秘密の新規混入 / 除外し忘れ / README 文言の変更 /
リンク切れ / 許可リストの陳腐化）で、すべて検出されることを確認しています。

### 初回公開までに踏んだ 2 つの穴

上記のゲートを揃えてもなお、**実際に公開版を動かすまで分からない**問題が
2 つ出ました。どちらも「除外の副作用」という同じ形です。

**1. workflow が一度も起動しなかった**

`ci.yml` は公開されたものの、トリガーが `push: [develop]` のままでした。
公開側は `main` 直 push 運用で `develop` が存在しないため、**何も走りません**。
README の CI バッジは「no status」になり、CI について書いた節の裏取りも
失われるところでした。公開側のブランチ運用に合わせる置換ルールを足して解決。

**2. 除外したファイルを読むテストが落ちた**

`render.yaml` を除外した結果、それを読む契約テストが `FileNotFoundError` に
なりました。ここで「ファイルが無ければ skip」にすると、**開発リポジトリ側で
誤って消したときも黙って skip** してしまい、テストが守る不変条件が抜けます。

同期スクリプトが `.portfolio-snapshot` マーカーを置き、その有無で分岐する
形にしました。

| 状態 | 挙動 |
|---|---|
| マーカーあり（公開版） | 意図的な除外なので skip |
| マーカーなし（開発リポジトリ） | 異常なので落とす |

### 塞ぎきれない穴と、その扱い

現在の検査は 4 つあります。

| 検査 | 検知するもの | 実行場所 |
|---|---|---|
| 秘密パターン走査 | 秘密の混入 | private CI + 同期時 |
| リンク検査 | 除外によるリンク切れ | 同期時 |
| 置換ルールの 1 回一致 | 元文言の変化 | 同期時 |
| **公開側 CI** | **除外によるコード / テストの破壊** | 公開リポジトリ |

4 つ目だけは静的検査で代替できません。「除外したファイルに依存するコードが
あるか」は、実際にビルドしてテストを走らせないと分からないためです。

そこで**公開側リポジトリを先に private で作り、CI の緑を確認してから
public に切り替える**手順にしました。公開側 CI 自体が最後の検査になります。

**学び**: **「見せないリスト」と「出させないゲート」は別物**。
前者は運用で必ず陳腐化するので、後者を最後の砦に置く。
そして後者を緩める方向の変更（パターンの削除）は禁じ、
例外は理由つきで、かつ棚卸しが強制される形でしか認めない。

もう一つ、**除外は「消す」ではなく「壊す」**。何かを公開対象から外すと、
それに依存していたコード・テスト・リンクが静かに壊れます。除外リストを
触ったら、静的検査だけで済ませず**公開版を実際に動かして確かめる**。

## 全体を通した振り返り

13 件の判断を並べると、いくつか繰り返し現れるパターンがあります。

| パターン | 該当 |
|---|---|

特に **§10 と §11 は、AI を活用した開発における失敗の典型**でした。AI は指示された範囲を高速に実行しますが、「その検索式は妥当か」「その変換は表現力を保つか」という**前提の妥当性は人間が担保する必要があります**。この経験は [AI_WORKFLOW.md](AI_WORKFLOW.md) の設計に直接反映されています。
