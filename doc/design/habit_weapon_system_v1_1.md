## 1. 本ノートの位置付け

Gemini から受領した「習慣×武器セット・育成機能 (MVP 版)」を Sabiowl 既存システム (FEAT-326/327 プレイヤー装備 + 6 軸 CharacterStat + Character ガチャ) と比較・整合性検証し、**v1.1+ で正式採用判断するための設計議論ベース**を確立する。

### 1.1 重要な認識: 既存「武器」と Gemini 提案「武器」は別軸

| 観点 | 既存 FEAT-326/327 (v1.0 確定) | Gemini 新提案 (v1.1+ 候補) |
|---|---|---|
| **装備対象** | プレイヤー個人 (1 人 1 武器、`is_equipped=True`) | **習慣単位** (1 習慣 ↔ 1 or N 武器) |
| **成長軸** | 固定 atk_bonus (5/10/20/35/50) | **習慣達成 → 武器 EXP → Lv 上昇 (+1, +2…)** |
| **紐付け先** | PlayerProfile (UniqueConstraint) | Habit (FK) |
| **UI** | PartyEditDialog 内 `EquipmentSelectionOverlay` (guild_equipment_2.md 準拠 Stack 重ね合わせ) | 習慣編集画面に「武器セット枠」+ 習慣一覧で武器アイコン + Lv 表示 |
| **報酬軸** | バトル damage 強化 (FEAT-326 で `equipped_weapon.atk_bonus` を damage 計算に反映) | **習慣達成の可視化** + Lv UP 演出 + (将来) 確率進化 |
| **未達 (サボリ)** | 該当なし | **ペナルティなし** (ストップ&ゴー、Sabiowl 聖域哲学整合) |
| **入手経路** | Shop コイン購入 + ガチャ排出 (両方既に実装) | Shop コイン購入 + ガチャ排出 (Q2 確定) |
| **コミット状態** | ✅ `a7d2fd6` / `c9eafbb` / `1270291` / `b252420` / `0ce737a` / `b5bdb22` | ❌ 未実装 |

→ **同じ「武器」キーワードを共有するが、設計コンセプトと UX 主軸が完全に独立**。共存可能。

### 1.2 v1.1+ FEAT-310 (既存装備拡張) との関係

`v1.1_roadmap.md §2-A` の **FEAT-310** は「バトル拡張フルスコープ (パーティ 3+1 + 装備拡張 + アビリティ + ジョブ SP/JP 育成 + 3 作戦カスタマイズ)」~25 営業日。この「装備拡張」は **既存 FEAT-326/327 プレイヤー装備の深化**:

- 装備強化システム (Lv 1-5 で atk_bonus +50%)
- セット効果 (剣 + 盾装備で防御 +10 等)
- 防具・アクセサリの 3 スロット制
- 武器の図鑑 + コレクション要素
- ガチャ排出武器の天井保証

→ FEAT-310 の「装備拡張」は **プレイヤー装備軸**、本ノートの「習慣単位武器育成」は **習慣達成可視化軸**。**両者は独立、相互に矛盾しない**。

## 4. Pre-mortem (PM 起票時想定、5 件、必須)

### #1 (カテゴリ 3, 最重要): 既存 CharacterStat 6 軸との成長軸衝突

現状: 「習慣達成 → カテゴリ → 6 ステータスに分散 EXP」(FEAT-213 で実装済)。武器追加 = **第 3 の成長軸** (キャラクター / 6 ステータス / 武器) が出現、ユーザーの注目点分散。

**予防策**: §5 の Q1 設計議論で「6 軸 vs 武器育成」の役割を決着させてから着手。

### #2 (カテゴリ 1, 6): Habit ↔ 武器多対多運用負担

既存ユーザーは複数の習慣 (10〜20 個) を持つ。Q3 確定「1 習慣 N 武器装備」を採用すると武器需要が増え、Shop で大量購入 → コイン枯渇 → グラインド化リスク。

**予防策**: Q3 採択時、N の上限 (例: 3 個まで) + EXP 配分ルール (均等 or 集中切替) を明確化。

### #3 (カテゴリ 8): 既存 FEAT-326/327 経路の回帰

`Player.equippedWeapon` + `EquipmentSelectionOverlay` + `PlayerWeapon` モデル + Shop 武器分岐 + ガチャ排出経路は既に契約テスト固定済 (`test_equip_weapon.py` / `test_shop_weapon_purchase.py` / `test_gacha_weapon_drop.py` / `test_player_weapons_view.py` / `equipment_selection_overlay_test.dart` 等)。新規「習慣単位武器」追加で既存テスト退行リスク。

**予防策**:
- 既存 PlayerWeapon は **そのまま維持** (プレイヤー装備軸)
- 新規 `HabitWeapon` モデル別途追加 (習慣装備軸)
- 名前空間明示で構造的に分離 (`WeaponMaster` 共有 or 別マスタ + 命名は議論)

### #4 (カテゴリ 6): UI 「2 種類の武器」混同

ユーザーが「自分の装備武器」と「習慣の武器」を混同するリスク。「攻撃力 +10 の銅の剣」がプレイヤー装備か習慣武器か区別困難。

**予防策**:
- 用語分離: プレイヤー装備 = 「武器 (Weapon)」、習慣装備 = 「武具 (Equipment)」or「お守り (Charm)」or「装具 (Gear)」(議論案)
- UI で表示位置を完全分離 (PartyEditDialog = プレイヤー装備 / 習慣編集画面 = 習慣装備)
- アイコン色 / 形を区別 (例: プレイヤー武器 = ⚔️ / 習慣武具 = 🛡️)

### #5 (カテゴリ 9): リリース後 MAU 観察前の機能投入

MAU 観察 (2026-07-08) なしに「習慣単位武器育成」を v1.1 即着手すると、**ユーザー価値の検証なしの推測実装**になり、`monetization_v1_1.md §1` 「8 割完成リリーススタンス」「月 3 万円ガードレール」哲学に反する。

**予防策**: v1.1 Phase 2 (2026-08 中旬) の MAU 観察データ (D30 継続率 / 機能別使用率 / Habit 編集画面訪問率) で投資判断。

## 5. Q1 成長軸設計 — 5 案分析 (別 PM 長期設計セッション引継ぎ用)

### 案 A) 両軸併存 (両方に EXP 付与) — 🟡 短期的に安全

- **仕組み**: 既存 6 軸はそのまま、習慣達成で 6 軸 + 武器の両方が上がる
- **メリット**: 既存 FEAT-213 マッピング破壊なし、最小実装
- **デメリット**: ユーザーの注目点が分散、「数値が増える画面が 2 つある」混乱
- **UX 評価**: ⚠️ シンプルさが失われる

### 案 B) 6 軸 = 「総合プロフィール」/ 武器 = 「個別習慣の達成可視化」 — ✅ **PM 強推奨**

- **仕組み**: 6 軸 = 「あなたという人の地層全体」、武器 = 「この習慣 1 つに対する達成の結晶」と役割分離
- **メリット**:
  - Sabiowl 公式比喩「地層 / 一石 / 羽」(CLAUDE.md サビ口調セクション) と整合
  - 既存ユーザー痛覚ゼロ
  - 段階拡張可能 (案 E のジョブシステムへ自然に進化)
- **デメリット**: 設計説明力が必要 (UI でどう住み分けを表現するか)
- **UX 評価**: ✅ 哲学完成度高、長期的に強い

**サビ口調案 (案 B の世界観)**:
> 「武器を磨くことは、その習慣を磨くこと。あなたの地層には、また一石が刻まれましたね。」

### 案 C) 6 軸縮減/廃止 + 武器が新主軸 — 🔴 高リスク

- **仕組み**: 6 軸を 3 軸に縮減 or 完全撤去、武器を中心軸に
- **メリット**: シンプル化
- **デメリット**: FEAT-213 マッピング破棄、既存ユーザーの「自分の 6 ステータス」喪失、痛覚大
- **UX 評価**: 🔴 既存ユーザーへの裏切り感

### 案 D) 6 軸 = 武器強化の素材化 — 🟡 中規模、デザイン次第

- **仕組み**: 6 軸数値 = 武器強化の消費素材 (例: 武器 Lv 5→6 には運動力 100 消費)
- **メリット**: 「6 軸を貯める意味」「武器を育てる意味」が連動、軸が 1 つに統合される
- **デメリット**: 6 軸が「努力で貯めた数値が消費される」設計 → 心理的抵抗 (「私の運動力が減った」誤読リスク)
- **UX 評価**: 🟡 説明次第、Sabi の聖域哲学とは少し距離

### 案 E) 案 B の拡張版 — 6 軸 = ジョブ解放条件 / 武器 = 各ジョブの装備 — 🔵 v1.2+ 完成形

- **仕組み**: 6 軸の値がジョブ解放条件 (戦士 = 運動力 50、賢者 = 学習力 50…)、武器は各ジョブに合った装備で進化分岐
- **メリット**: 「習慣 → 6 軸 → ジョブ → 武器 → 戦闘」全体像が綺麗、Gemini 案の「将来拡張ジョブシステム」と完全整合
- **デメリット**: 規模が大きく、v1.1 では着手困難、v1.2+ 領域
- **UX 評価**: ✅ 完成形のロードマップ、案 B から自然進化

### PM 強推奨: **案 B → 案 E のロードマップ**

| バージョン | 採用案 | 規模 | 内容 |
|---|---|---|---|
| **v1.0** | なし (採用記録のみ) | 0h | 設計議論待ち |
| **v1.1** | **案 B 採用** | ~25h | 6 軸 = 総合プロフィール / 武器 = 個別習慣の達成可視化 |

## 6. データモデル設計 (案 B 採択時、v1.1 着手準備)

### 6.1 既存モデル (v1.0 確定、変更なし)

| モデル | 役割 | 触らない |
|---|---|---|
| `WeaponMaster` | プレイヤー装備武器マスタ (5 種 seed 済) | ✅ |
| `PlayerWeapon` | プレイヤー装備所持 (is_equipped UniqueConstraint) | ✅ |
| `CharacterStat` | 6 軸ステータス (運動力/学習力/...) | ✅ |
| `Habit` / `HabitLog` | 習慣定義 + 日次実績 | ⚠️ 逆参照追加検討 |

### 6.2 新規モデル (v1.1 着手時に追加)

#### A. HabitEquipmentMaster (仮、案 B 採択時)

> Pre-mortem #4 用語分離を採択した場合の命名。「Habit に装備するもの」を意味する `Equipment` を採用、`Weapon` (プレイヤー装備) と衝突回避。

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | AutoField | PK |
| `key` | CharField(32, unique=True) | 識別子 (例: `rusty_sword` / `wooden_shield`) |
| `name` | CharField | 表示名 (例: 「サビた古剣」) |
| `image_asset_path` | CharField | Flutter 側ドット絵パス |
| `category_type` | CharField | 属性 (運動 / 学習 / 健康 / etc.、Habit カテゴリと整合) |
| `description` | TextField | 説明文 |
| `base_exp_to_level_up` | IntegerField | Lv 1 → 2 に必要 EXP (例: 100) |
| `max_level` | IntegerField | 上限レベル (案 B 推奨 = 10、進化はジョブシステム連動で v1.2+ 案 E) |

#### B. HabitOwnedEquipment (仮)

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | AutoField | PK |
| `player` | FK(PlayerProfile) | プレイヤー |
| `equipment` | FK(HabitEquipmentMaster) | 装備マスタ |
| `habit` | FK(Habit, null=True) | 紐付け先 (未装備 = null) |
| `level` | IntegerField(default=1) | 現在の Lv |
| `experience` | IntegerField(default=0) | 現在の Lv 内 EXP |
| `acquired_at` | DateTimeField(auto_now_add=True) | 取得日時 |

**重要**: Q3 採択「1 習慣 N 装備」のため、`habit` への UniqueConstraint は **しない** (1 つの Habit に複数の HabitOwnedEquipment が紐付けられる)。N の上限は **アプリケーション層で検証** (例: 1 Habit に最大 3 装備)。

#### C. Habit (既存) への逆参照

`Habit.equipped_items` は `HabitOwnedEquipment.habit` の逆参照で自然に取得可能 (新規フィールド追加なし)。

### 6.3 EXP 配分ルール (Q3 採択時の必須詳細設計)

「1 Habit に N 装備、習慣達成で 1 つの EXP が発生 → どう分配?」を決める必要あり。3 案:

| 配分案 | 仕組み | UX 評価 |
|---|---|---|
| **均等分配** | N 装備に EXP を 1/N ずつ分配 | シンプル、ただし「全部育つが遅い」 |
| **集中育成切替** | ユーザーが 1 個「主装備」を選択、EXP 100% その装備に | 戦略性高、ただし UI 切替操作必要 |
| **比率指定** | ユーザーが各装備に 0-100% 配分指定 | 完全自由、ただし UI 複雑度高 |

**PM 推奨**: **均等分配を v1.1 MVP**、v1.2+ で集中育成切替追加が漸進的。

## 8. ガチャ排出設計 (Q2 ガチャ + ショップ両方)

既存 FEAT-326 で武器ガチャ排出は実装済 (Daily SR mythril / Weekly SSR dragon_slayer)。**習慣装備のガチャ排出は別 reward_type で追加**:

```python
# backend/api/views/gacha.py 既存
```

### 11.5.4 統合 Pre-mortem 追加 #6-8 (FEAT-379 由来)

#### #6 (カテゴリ 8): FEAT-379 v1.0 仕込み経路の v1.1+ 装着 UI 解禁時の段階移行リスク

v1.0 で結晶カウンターを実数加算してきたユーザーが、v1.1+ 解禁時に「累積 100 個」状態で初めて装着 → 全部装着可能 → 即座にゲームバランス崩壊。

**予防策**: v1.1+ 解禁時に **取り外しコスト + 1 武器あたりソケット上限 3 + コイン制約** で構造的にバランス保護。リリース前に PostHog で「v1.0 期間中の累積結晶数分布」を計測、v1.1+ バランス設計に反映。

#### #7 (カテゴリ 3): FEAT-378 + FEAT-379 統合実装の規模膨張

FEAT-378 単独 ~25h + FEAT-379 v1.1+ 解禁 ~15h + 統合議論で追加された連携機能 ~5h = **総計 ~45h** = 🔴 大規模超 (1 ヶ月以上)。

**予防策**: 統合 PM 長期設計セッションで Phase 分割を明示:
- Phase A (v1.1 P2 早期、~15h): FEAT-379 v1.1+ 装着 UI 解禁 (Q2-Q5 限定スコープ)
- Phase B (v1.1 P2 中期、~25h): FEAT-378 案 B 採用 + 用語整理 (Q1 + Q8)
- Phase C (v1.2+、~30h): FEAT-378 案 E + FEAT-379 シナジー拡張 + 結晶合成 (Q6 + Q7 + 新規)

#### #8 (カテゴリ 6): UI 統合時の武器画面情報過多

PartyEditDialog の EquipmentSelectionOverlay (FEAT-327) に「ソケット枠 + 結晶アイコン + 習慣武器育成 EXP バー + プレイヤー武器属性」すべて表示すると情報過多で操作不能。

**予防策**: v1.1+ 解禁時に **Tab 切替** (装備 / ソケット / 育成) or **段階表示** (デフォルト最小、タップで詳細展開) で UI 情報量を制御。
